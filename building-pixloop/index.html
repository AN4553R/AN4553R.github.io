PixLoop · Engineering notes · October 2026

The Phone Had the Photo. The Camera Had Its Doubts.

I wanted an easier way to move camera-selected photos from my Sony ZV‑1 to my phone. Then a JPEG reached Photos, but the camera still said the transfer was cancelled.

A Sony ZV‑1 · SwiftUI · A project in progress · 6 min read

I started PixLoop because Sony’s Imaging Edge Mobile felt dated, like an app from a decade ago. On October 18, 2026, its U.S. App Store listing showed 1.6 stars from around 6.7K ratings. I wanted to transfer photos I chose on my ZV-1 to my phone, then browse the originals in a simple gallery. I wanted no account and no cloud service.

I started with the wrong protocol

I searched for a way to communicate with the camera and found PTP/IP on port 15740. The Camera & Imaging Products Association’s DC-005 standard defines PTP over TCP/IP. I tried that protocol. The standard does not say that the ZV‑1 uses PTP/IP for Send to Smartphone.

PixLoop connected over PTP/IP, but it could not transfer the selected photos. I had searched for a camera protocol without checking the ZV‑1’s specific phone-transfer workflow.

I found the protocol details in the open-source ImagingEdge4Linux project. Its README describes SOAP for Send to Smartphone and PTP/IP for Send to Computer. I read the project’s imaging-edge.py source. It showed the endpoint and SOAP operations. The ZV‑1 uses Sony’s UPnP/SOAP services over HTTP at 192.168.122.1:64321. I tested that flow on my ZV‑1.

Conceptual transfer sequence

On my first real transfer, the JPEG reached Photos. The Sony ZV‑1 still said Sending cancelled.

I had built the download steps but missed the final acknowledgement. I could open the file, so I thought the transfer had finished. The camera was waiting for PixLoop to send X_TransferEnd. Without that message, it could treat a good download as a failed transfer.

Retries need a stable photo identity

The camera assigns each file a number called a handle. That number can change after reconnect. If PixLoop treats it as the photo’s identity, it can mistake a previously received photo for a new one or request the wrong file.

For Sony SOAP files, PixLoop uses the original resource URL from the camera’s listing as the file key. If a transport does not provide a source URL, PixLoop uses the file name, size, and capture time in whole seconds. This fallback can match different files, so it does not guarantee identity across reconnects.

PixLoop also records the Photos asset created by each transfer. Before it skips a file, it checks that the corresponding asset still exists. If someone deletes the asset, PixLoop can download the file again.

The camera network had no internet

The camera’s Wi‑Fi network has no internet access. iOS may report that the phone has no internet route even while the camera connection still works. My first connection logic treated that report as a disconnection and dropped the camera link.

I changed the app to track internet access and camera access separately. I also made background reconnects distinct from a person tapping Connect, so the app responds to that tap.

Photos called the image handler more than once

The Photos framework can call an image request handler more than once. It may send a quick preview first, then the full image. I wrapped the callback in async code with a continuation that expected one result. The second callback tried to resume that continuation again, and the app crashed.

Swift checks that a continuation receives the correct type. It does not prevent the framework from calling the handler more than once. I added a guard so only the first final callback can resume the continuation.

I also wanted to avoid changing the camera file during import. PixLoop adds the downloaded file resource directly to the Phone Photos Album instead of creating a new image from a rendered preview. That avoids re-encoding the image during this step; I have not independently verified byte-for-byte preservation or every metadata field.

Interface bugs stopped basic actions

The interface had its own bugs. A long press intercepted the tap that should open a photo. Another gesture could leave the photo viewer stuck. The “Learn More” button responded only when someone tapped its text.

KiroCrew helped me build the prototype and implement PixLoop. I used ChatGPT to shape its visual identity. Codex helped me test and challenge KiroCrew’s work. I checked the transfer flow on my own ZV‑1.

Where PixLoop stands

JPEG transfers work with multiple photos on my ZV‑1. Received files go into a PixLoop album in Photos. I can cancel queued files or the rest of a batch without removing files already saved.

In one real-device run, a 4.75 MB JPEG reached Photos in about 1.8 seconds. I have not measured enough transfers to make a general speed claim. I still need to test video and RAW. Then I will decide whether to prepare PixLoop for the App Store, support more cameras, or keep it for myself.
