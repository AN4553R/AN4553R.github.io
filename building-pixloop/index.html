PixLoop · Engineering notes · October 2026

The photo arrived. The camera said “cancelled.”

I wanted an easier way to move camera-selected photos from my Sony ZV‑1 to my phone. Then a JPEG reached Photos, but the camera still said the transfer was cancelled.

A Sony ZV‑1 · SwiftUI · A project in progress

I started PixLoop because Sony’s Imaging Edge Mobile felt dated, like an app from a decade ago. I wanted to transfer photos I chose on my ZV‑1 to my phone, then browse the originals in a simple gallery. I wanted no account and no cloud service.

I started with the wrong protocol

At first, I built the transport around PTP/IP on port 15740. The Camera & Imaging Products Association’s DC-005 standard defines PTP over TCP/IP networks. That made PTP/IP seem like a reasonable choice for camera communication. But the standard did not say that the ZV‑1 uses it for Send to Smartphone.

PTP/IP connected. It failed to transfer the selected photos. I chose it because I knew it as a camera-tethering protocol. I had not checked how the ZV‑1 sent selected photos to a phone.

I found the protocol details in the open-source ImagingEdge4Linux project. Its README describes SOAP for Send to Smartphone and PTP/IP for Send to Computer. I read the project’s imaging-edge.py source. It showed the endpoint and SOAP operations. The ZV‑1 uses Sony’s UPnP/SOAP services over HTTP at 192.168.122.1:64321. I tested that flow on my ZV‑1.

The source showed this transfer sequence:

  1. Start the transfer.
  2. Read the camera’s push queue.
  3. Download each selected original and save it to Photos.
  4. Send the final acknowledgement.

On my first real transfer, the JPEG reached Photos. The Sony ZV‑1 still said Sending cancelled.

I had built the download steps but missed the final acknowledgement. I could open the file, so I thought the transfer had finished. The camera was waiting for PixLoop to send X_TransferEnd. Without that message, it could treat a good download as a failed transfer.

I also found bugs in file identity, network handling, Photos callbacks, and interface actions.

Retries need a stable photo identity

The camera assigns each file a number called a handle. A handle can change after the app reconnects. If PixLoop uses that handle as the file’s identity, a retry can treat an old photo as new. It can also select the wrong photo.

I changed how PixLoop identifies each photo. It now uses a stable source identity. It records the Photos asset it created and checks that the asset still exists before skipping a transfer. If someone deletes the photo, the next run can download it again.

The camera network had no internet

The camera’s Wi‑Fi network has no internet access. iOS may report that the network route is unavailable while the phone remains connected to the camera. My first connection logic read that report as a disconnection and dropped the working camera link.

I changed the app to track internet access and camera access separately. I also made background reconnects distinct from a person tapping Connect, so the app responds to that tap.

Photos called the image handler more than once

The Photos framework can call an image request handler more than once. The handler may return a quick preview first, then the full image. I wrapped the callback in async code with a continuation that expected one result. Photos called the handler again, and the app tried to resume the continuation twice. The app crashed.

Swift checks the continuation’s types. It cannot control how many times the framework calls the handler. I added a guard so a second callback cannot resume the continuation.

I also needed to preserve the camera original. PixLoop imports the downloaded resource directly into Photos. This keeps the original bytes and metadata. The app can process a preview while leaving the source file unchanged.

Interface bugs stopped basic actions

The interface had its own bugs. A long press intercepted the tap that should open a photo. A gesture sequence could leave the viewer stuck. The “Learn More” button responded only when someone tapped its text.

Each bug made an action behave differently from how it looked. A photo should open when someone taps it. A button should respond across its full area. The app should show what it is doing and offer a recovery step when something fails.

I also struggled with the app icon. I generated three rounds of icons in code and disliked them all. I switched to the ribbon emblem I wanted and prepared it for the app.

KiroCrew helped me build the prototype and implement PixLoop. I used ChatGPT to shape its visual identity. Codex helped me test and challenge KiroCrew’s work. I checked the transfer flow on my own ZV‑1.

Where PixLoop stands

JPEG transfers work with multiple photos on my ZV‑1. In one real-device run, a 4.75 MB JPEG reached Photos in about 1.8 seconds. I have not measured enough transfers to make a general speed claim. I still need to test video and RAW. After those tests, I will decide whether to prepare PixLoop for the App Store, add support for more cameras, or keep PixLoop for myself.

App Store context: On Oct 24, 2026, the U.S. App Store listing showed Imaging Edge Mobile at 1.6 stars from 6.7K ratings.
